> 一个 50 条真实客服问题的 golden set 能抓住合成大测试集漏掉的 RAG 回归，关键是检索与生成分开打分、真实而非合成的提问方式。
>
> 直接对应读者想学的 LLM 应用评测方法：给出可落地的小型 golden set 设计与 CI 门禁流程。

## 摘要

团队用约 5000 条合成问题评估 RAG 助手一年，分数波动只有零点几个百分点，没人信任；一次 reranker 改动悄悄破坏了所有定价类问答，大测试集也没发现。他们改用 50 条来自支持工单的真实问题，每题标注必须命中的文档和答案必须包含的 2-3 个事实，两人一个下午建好。之后每个涉及检索、分块、prompt 或模型改动的 PR 都跑这 50 题，检索按 recall@5 单独评分，答案由第二个模型按 rubric 打分，任何从「事实全中」下滑的题都阻塞合并。最终捕获的回归中 70% 来自检索，chunk size 改动最危险。

## 核心观点

- 合成问题过于干净、措辞规范，无法暴露真实用户表述含糊带来的检索失败，真实工单问题才能触发。
- 检索质量与生成质量必须分开度量：先用 recall@5 判断必需文档是否进入前 5 个 chunk，再评答案事实覆盖，出问题时能立刻定位是检索还是生成。
- 评分 rubric 用四档：事实全中、部分、全无、与来源矛盾；只看相对退步（从全中下滑）而非绝对分数，避免分数微小波动带来的噪声。
- 小集合只做回归门禁，不负责发现罕见失败；稀有 case 靠每周抽样生产对话兜底。
- chunk size 从 800 改到 400 token 对短 FAQ 的 recall 有提升，却破坏了多步 how-to 类回答，说明该参数需要按问题类型分别验证。

## 实践方法

1. 从真实支持工单中挑选 50 条有代表性的问题，覆盖主要用户意图。
2. 为每题标注：必须被检索到的文档，以及答案必须包含的 2-3 个事实。
3. 在 CI 中对每个触及 retrieval / chunking / prompt / model 的 PR 跑这 50 题。
4. 检索侧计算 recall@5：必需文档是否出现在前 5 个 chunk 中。
5. 生成侧用第二个 LLM 按 rubric 打分：事实全中 / 部分 / 全无 / 与来源矛盾。
6. 设置门禁：任何题目从「事实全中」下滑即阻塞合并，需人工复核。
7. 每周抽样生产对话，弥补 50 题覆盖不到的长尾失败。

## 下一步行动

- [ ] 为自己的 RAG 项目从真实日志/工单里挑 20-50 条问题，标注必需文档与必含事实，做成 CI 门禁。
- [ ] 在现有评测中把检索 recall@k 与生成质量拆成两个指标分别报告。
- [ ] 对比测试 chunk size 改动（如 800 vs 400 token）在 FAQ 类与多步问答类问题上的 recall 差异。

## 局限与存疑

- 单产品、单文档集（约 2000 页）的经验，未验证多语言内容；50 题检测不到罕见失败；46/50 的模型-人工一致率意味着仍有约 8% 误判；grader 代码约 120 行 Python，未在文中给出；本文是为 AI Curator demo 写的示例文章，非真实博客。
